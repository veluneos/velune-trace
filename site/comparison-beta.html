먼저 이런 팀들과 함께 검증하고 있습니다.

명확한 Reference–Target 비교 니즈가 있는 소수의 팀과 먼저 시작한 뒤, 점차 범위를 넓혀갈 예정입니다.

Before/After를 비교하는 팀

소프트웨어, 설정, 센서 업데이트 이후 어떤 관측값과 조사 구간이 달라졌는지 확인해야 하는 팀

반복 실행을 수동으로 검토하는 팀

원본 로그를 외부로 전송할 수 없는 팀

원본 로그는 내부에 유지하면서, 제한된 파생 구조만 외부에서 처리하도록 허용해야 하는 팀

동작 방식

로컬에서 준비하고, VeluneOS에서 비교하세요.

준비 과정에서 원본 MCAP은 로컬 환경에 유지됩니다. 업로드되는 것은 파생 파일 하나 — comparison.velune — 뿐입니다.

STEP 01

Reference Run + Target Run

비교 기준이 되는 실행(Reference)과 비교 대상이 되는 실행(Target)을 선택합니다.

STEP 02

Prepare locally

Velune Adapter가 두 실행을 로컬에서 하나의 comparison.velune 파일로 만듭니다. 원본 MCAP은 로컬 환경을 벗어나지 않습니다.

STEP 03

comparison.velune 업로드

준비된 파일 하나를 VeluneOS Compare에 업로드합니다.

STEP 04

구조적 차이 확인

Reference와 Target 사이에 무엇이 달라졌는지, 어디부터 봐야 하는지 확인합니다.

Data Boundary

Beta 운영 방식

운영 모델을 먼저 검증한 뒤 자동화합니다.

초기 Private Beta

Comparison Engine이 리포트를 생성하고, VeluneOS 운영자가 입력 오류와 실행 상태를 검토하는 서비스 주도형 운영 방식입니다.

  • Bundle 스키마 및 지원 가능 여부 사전 확인
  • Comparison Job 실패 처리
  • 엔진이 생성한 리포트 품질 검토
  • 엔지니어 피드백 수집
자동화된 운영 방식

고객이 Bundle을 직접 업로드하면 서버가 검증, 비교, 리포트 생성, 피드백, 삭제까지 자동으로 처리하도록 서비스가 발전합니다.

  • 자동화된 Reference–Target 비교
  • Report URL, JSON, Markdown 형태로 전달
  • 조직 단위 접근 및 보존 정책 관리
  • 운영자는 예외 상황만 처리
